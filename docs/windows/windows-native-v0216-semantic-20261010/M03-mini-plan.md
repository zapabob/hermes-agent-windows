## Admission, cancellation and resource ownership

Serialize callback admission and cancellation under the existing shared flow lock. Before admission, cancellation ends the pending flow, wakes both waiters and retains the first cause. After an accepted code or error callback, cancellation reports that the operation was not cancelled and leaves its eventual real success/error result intact. Approved and already settled results remain stable. Do not remove, restore or claim rollback of already admitted token/config/manager state.

Within the Gateway session owner, reserve pending capacity atomically before acquiring listeners or starting workers. Use one monotonic deadline across admission waits. A failed or held acquisition retains the ownership necessary for recovery. Garbage collection must not forget a live resource or a flow whose shutdown is uncertain. A worker-complete flag is not sufficient proof of listener closure. Gateway cancellation followed by a newly started flow must perform token persistence, reconnect the real runtime and execute the protected registry nonce operation. REST startup uncertainty and TTL garbage collection retain their existing behavior and require separate qualification; REST acceptance here covers issuer relay, profile authority and callback cancellation.

Direct Python resource oracles retain the actual worker/listener/loop references and require their observed closure or thread exit before fixture cleanup. Anonymous rejection observes the real server/socket/thread lifecycle. Actual dev Electron proof observes public preload listen/cancel, callback listener refusal, captured profile, token storage, protected tools/call and owned process identities. Electron process exit/listener refusal does not directly establish an in-process Python loop closure or worker join; direct Python oracles supply their own bounded observations.

Fresh-process proof uses the same owned persisted HOME in a new Windows Python process, an actual birth/observed handshake and registry dispatch. An owner token enables its real protected effect; a foreign peer without its own token receives neither borrowed authentication nor effect. The child asserts closure/not-running and bounded join/not-alive for any existing MCP core loop/thread before writing its final receipt; no loop/thread flags are stored in that receipt.
