The actual Windows restart caller in `hermes_cli/gateway.py` launches a Python `-c` watcher with a future `hermes_cli.main gateway run` command in its argv. The original N52 implementation, recorded as local commit `ad6fb9c1f9185027ff3ec66f8feba5bb18135585`, rejects the watcher's future argv when deciding whether the *current* process is a Gateway or updater holder. Seven of that candidate's eight product blobs transferred unchanged into this stack. The remaining `update_cmd.py` was adapted to the current main source without importing an unrelated stash-selector change from the old parent.

Independent integration review found another caller of the same ownership boundary: `_orphaned_desktop_backend_pids` and `_handoff_reapable_backend_pids` used a whole-command-line substring test for `serve` or `dashboard`. A valid Gateway profile named `serve` appears in the future command of the watcher. Two new tests reproduced the error on the stacked candidate: the handoff path returned the watcher's PID as a Desktop backend and the orphan path returned its PID and start-time fingerprint. Both tests failed before the correction. Both reapers now use the existing parser-derived `_looks_like_desktop_control_plane` classifier, which rejects inline Python source and still accepts actual `serve` and `dashboard` commands.

The focused reaper/Desktop tests passed 32/32. The final selected integration set passed 197/197, with 17 dependency deprecation warnings. Ruff passed for all ten product paths, and the staged diff check was clean. The old substring implementation was a live two-test counterexample, while three controlled mutants from the original N52 candidate remain historical evidence for its seven unchanged blobs. We do not add those counts to any campaign total.
