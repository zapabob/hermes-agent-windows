## Minimal correction and observed result

The Windows ADS path now validates the named-stream target, opens and checks the base through a held handle, creates the stream exclusively, writes and flushes its bytes, and reads them back. It never uses os.replace for an ADS target. It removes a newly created partial stream after a known write failure, without deleting a pre-existing or racing stream. NTFS has no separate stream timestamps, so the restore skips the ordinary-file os.utime path; changing a stream can update base-file metadata. The tested invariant is preserved base-file bytes and verified stream bytes, not byte-identical base-file metadata. See Microsoft's [file-stream semantics](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams) and [CreateFile disposition](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea).

Before the ADS effect, the vault commits pending_restore_outcome and the exact restore_target, including a custom destination. Known collision or successful rollback clears that pending claim. When cleanup fails, or the ADS lands but final SQLite recording fails, the row and encrypted blob remain pending across store reopen and both restore and delete reject the item. The status API and Desktop Security view distinguish this pending result and disable item actions. The delete path also rereads the row under BEGIN IMMEDIATE and validates stored findings before unlinking the blob; the corresponding stale-client and corrupt-evidence tests were RED before the final corrections. Pending is evidence for reconciliation, not an assertion that the stream exists or is safe to retry.
